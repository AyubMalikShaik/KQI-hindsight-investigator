Business Anomaly Investigator: Technical Architecture

One-line pitch: An autonomous investigation agent that turns a KPI alert into an evidence-backed root-cause report, and gets measurably better with every investigation because it remembers outcomes (Hindsight).

Winning angle: Most "AI analyst" demos are chat-over-SQL. Yours is different in three ways: (1) it is triggered by alerts, not questions; (2) it validates hypotheses with evidence instead of guessing; (3) it learns from human-confirmed outcomes. Build the architecture around these three ideas.

Positioning: this is not the "Incident Response Agent" from the brief's idea list. That one handles infrastructure outages. This one investigates business KPI anomalies (revenue, conversion, churn) across data, events and logs. Say this in the first sentence of your pitch.

1. Layered Architecture (Overview)

  B --> C[L3 Agent Core: LLM + Function Calling]

  D --> E[L5 Data Layer: DuckDB / SQLite / CSV / Parquet]
  C <--> F[L6 Memory Layer: Hindsight recall / retain / reflect]

  H --> I[L9 Experience Layer: Streamlit + Plotly]
  I --> J[Human Feedback: confirm / reject cause, action taken, outcome]
  J --> F
  K[L10 Platform: config, observability, audit, security, eval] -.-> B
  K -.-> C
Layer Responsibility Tech
L1 Ingestion Receive anomaly alerts from any monitoring system, normalize to one schema FastAPI webhook (or Streamlit button for demo), Pydantic
L2 Orchestrator Runs the investigation lifecycle, budgets, retries, timeouts Python state machine
L3 Agent Core Plans, calls tools, forms and tests hypotheses Groq LLM (function calling)
L4 Tool Layer Deterministic, generic, typed analysis functions Python + Pandas + DuckDB
L5 Data Layer KPI facts, dimensions, related metrics, business events, logs DuckDB / SQLite
L6 Memory Store and recall past investigations, causes, actions, outcomes Hindsight Cloud + hindsight-client
L7 Validation Score evidence, reject weak hypotheses, compute confidence Python rules + LLM critic
L8 Report Structured, auditable output Pydantic to JSON, Markdown
L9 Experience Live investigation view, report, feedback Streamlit, Plotly
L10 Platform Config, logging, audit trail, eval, security structlog, pytest, .env / secrets

Key design principle: The LLM never touches raw data directly and never writes free-form SQL against production tables. It only calls typed tools that return compact, structured evidence. That is what makes it safe, cheap, and enterprise-credible.

2. Layer-by-Layer Detail

L1: Alert Ingestion

Normalize every alert into one Anomaly object so the system is monitoring-tool agnostic (Datadog, Grafana, custom job, all the same).

{
  "alert_id": "ALR-2026-0142",
  "metric": "daily_revenue",
  "grain": "day",
  "detected_at": "2026-09-27T06:00:00Z",
  "anomaly_window": {"start": "2026-09-26", "end": "2026-09-26"},
  "baseline_window": {"start": "2026-08-29", "end": "2026-09-25"},
  "observed": 84200, "expected": 121000, "deviation_pct": -30.4,
  "direction": "drop", "severity": "high", "source": "grafana"
}

Also build a Scenario Simulator (inject a known anomaly into synthetic data). It powers the demo and the evaluation harness.

L2: Investigation Orchestrator

An explicit state machine (not a single giant prompt) so every run is bounded and traceable:

RECEIVED -> SCOPING -> RECALL_PRIOR -> EVIDENCE_GATHERING -> HYPOTHESIZING
-> VALIDATING -> (loop back to EVIDENCE_GATHERING if confidence < threshold)
-> REPORTING -> AWAITING_FEEDBACK -> CLOSED (retained to memory)

Controls: max tool calls (e.g. 15), max validation loops (e.g. 2), per-tool timeout, token budget, and a stop condition ("top hypothesis confidence at least 0.75 OR budget exhausted, then report with honest uncertainty").

Every state transition is written to an investigation trace (JSONL). This trace drives the live UI and the audit log.

L3: Agent Core (LLM + Function Calling)

Use separate logical roles, but merge them into 3 LLM calls per investigation (Plan+Hypothesize, Validate, Report) so the Groq free tier is not exhausted mid-demo. Recommended models: openai/gpt-oss-120b primary, qwen/qwen3-32b fallback. The roles:

  1. Planner: given the anomaly plus recalled memories, outputs an investigation plan (which tools, which order).
  2. Investigator: executes tool calls via function calling, summarizes each result into an evidence item.
  3. Hypothesizer: proposes ranked candidate causes, each with predicted evidence ("if X is the cause, we should also see Y").
  4. Critic/Validator: checks each hypothesis against gathered evidence, requests targeted tests, flags contradictions.
  5. Reporter: writes the final structured report.

The "predicted evidence" step is the differentiator: it turns validation into a real test (falsifiable), not narrative.

ToolCallGuard (function-calling error handling, required by the brief)

Every tool call passes through one guard layer:

Failure Handling
Malformed JSON arguments Attempt one automatic repair, else re-prompt the model with the tool schema
Unknown tool / invalid parameters Return a structured error to the LLM so it self-corrects (max 2 tries)
Model returns no tool call or garbage Retry, then switch to the fallback model
Groq rate limit / timeout Exponential backoff; cache tool results keyed by (tool, args hash)
Repeated identical calls (loops) Stop after 3 repeats and force the next stage
Budget exhausted Report with honest uncertainty instead of failing

Log every guard event to the trace and unit-test each row. Judges can see robustness.

L4: Generic Investigation Tools

Tools are generic and metric-agnostic, driven by a semantic catalog (L5), so the same agent works on revenue, churn, latency, or conversion.

Tool Input Output (structured)
analyze_metric metric, windows trend, baseline vs. anomaly, seasonality-adjusted deviation, z-score, changepoint date
breakdown_by_dimension metric, dimension(s), windows contribution to change per segment (top N), concentration score, mix-shift vs. rate-shift
find_related_metrics metric correlated/causally-linked metrics from the catalog with their deviations (e.g., traffic, conversion, AOV)
query_business_events time range, filters deployments, pricing changes, campaigns, outages, holidays, promotions near the changepoint
analyze_logs (optional) service, time range error-rate spikes, top error signatures
compare_cohorts two segments statistical difference test
recall_similar_investigations evidence summary Hindsight results (see L6)

The important technical detail: driver decomposition. For a sum metric, compute each segment's contribution to the total change, and split it into volume effect vs. rate effect. This gives mathematically defensible attribution ("62% of the drop comes from Android users in India, and it is a conversion-rate effect, not a traffic effect"). Judges will remember this.

Each tool returns: {finding, numbers, confidence_hint, chart_spec, evidence_id}. The chart_spec lets Streamlit render Plotly charts automatically for each evidence item.

Guardrails: read-only DB connection, parameterized queries only, allow-listed tables/columns from the catalog, row and time limits.

L5: Data Layer

Use DuckDB for analytics (fast, embedded, reads Parquet/CSV). Suggested schema:

fact_kpi(date, metric, value, <dimension columns...>)
dim_catalog(metric, description, unit, aggregation, dimensions[], related_metrics[])
business_events(event_id, ts, type, service, description, owner, metadata)
logs_summary(ts, service, level, signature, count)          -- optional
investigations(id, alert_id, status, started, finished, report_json, feedback_json)

Semantic catalog (dim_catalog) is the enterprise-ready move: it tells the agent what each metric means, how it aggregates, and which dimensions and related metrics exist. Onboarding a new KPI = adding a catalog row, no code change.

Seed 3 to 4 realistic scenarios with planted root causes:

  1. Regional payment gateway failure (dimension: country + payment method)
  2. Bad app release (dimension: app version + platform)
  3. Pricing/promo change (mix shift in AOV)
  4. Tracking bug (a data-quality false alarm, so the agent must say "the KPI is wrong, not the business")

Scenario 4 is a strong differentiator: real agents must detect data quality issues.

Realistic data strategy (the brief calls this the #1 thing that makes a project look real):

  • Base facts: a real Kaggle dataset, e.g. Olist Brazilian e-commerce (orders, payments, customers, regions), aggregated into fact_kpi.
  • Have the LLM generate business_events: deploy names (checkout-service v4.12.0), campaign names, vendor outages, pricing changes, with owners and timestamps.
  • Generate realistic log signatures (PaymentGatewayTimeout: upi-sdk 4.12.0 (504)).
  • Plant root causes at known dates so accuracy can be scored automatically.
  • Write past investigations with real-sounding postmortem notes for the Hindsight backfill.

L6: Memory Layer (Hindsight)

This is your core innovation, so design it deliberately. Use a dedicated memory bank per tenant/team (e.g., anomaly-investigator::<org>).

What to retain (after human feedback), one memory per closed investigation:

Metric: daily_revenue (drop 30%) | Segment: IN / Android / UPI
Evidence: conversion -41% in IN-Android-UPI, traffic flat, deploy v4.12 at 05:40 UTC,
          payment error rate 0.4% -> 27%
Root cause (confirmed): UPI SDK timeout regression in app v4.12
Action taken: rollback to v4.11
Outcome: revenue recovered in 3h
Agent's initial top hypothesis: <x> | Correct? yes/no | Time to resolve: 3h

Use context and tags (metric, dimension, cause_type, outcome) so recall can filter.

When to recall (twice per investigation):

  1. After scoping: query from the anomaly signature ("revenue drop, single-country, mobile-only, post-deploy").
  2. After evidence gathering: query from actual findings to fetch causes that matched similar evidence patterns.

How recalled memory is used: as hypothesis priors, never as truth. The Hypothesizer receives them labeled as "past cases", and the Validator must still confirm with current data. Report explicitly shows: "Similar to INV-0098 (rollback fixed it). Confirmed here by X, Y." This prevents anchoring and is a strong trust story.

Reflection: periodically (or on demand) use Hindsight's reflect capability to produce org-level insights ("60% of mobile-only revenue drops in the last quarter were release regressions"). Show that in a "What the org has learned" dashboard panel.

Verify exact hindsight-client method names and parameters against the current Hindsight docs before coding. Wrap them in your own MemoryService class (recall(), retain(), reflect()) so the rest of the app never depends on SDK details.

Making memory the star (25% of judging):

  1. Backfill history. Before the demo, retain 15 to 20 past investigations with older timestamps (weeks back), so the agent visibly recalls context from the past.
  2. Two-stage retain. Retain an unconfirmed record right after the agent finishes, then retain the confirmed outcome after human feedback. Memory grows on every run, and outcomes refine it.
  3. Show recalled memories on screen for every run (a "Memory used" card: which past cases, why similar, whether they helped).
  4. Learning curve. Run 10 to 20 incidents in sequence and plot steps-to-root-cause, time-to-report and hypothesis accuracy against incident number, with a no-memory baseline line. Interaction 1 is generic, interaction 5 is faster, interaction 20 feels like it knows the organization. This chart is your headline.
  5. Document it in docs/hindsight_usage.md: what is retained, when recall happens, what reflect produces, plus before/after evidence.

L7: Validation and Confidence Engine

Do not let the LLM just state a confidence number. Compute it:

confidence = w1*evidence_support + w2*temporal_alignment + w3*magnitude_explained
           + w4*memory_prior - w5*contradictions
  • Evidence support: fraction of the hypothesis's predicted evidence actually observed.
  • Temporal alignment: did the candidate cause precede the changepoint?
  • Magnitude explained: share of the deviation attributable to the affected segment.
  • Memory prior: small boost if a similar past case was confirmed.
  • Contradictions: evidence that argues against it (e.g., traffic also dropped elsewhere).

Also include: data-quality checks (null spikes, duplicate loads, late-arriving data), counterfactual check (metric with the suspected segment removed: is the anomaly gone?), and a "cannot determine" outcome when evidence is weak. Honest uncertainty is an enterprise trust signal.

L8: Report Generator

Enforce a Pydantic schema so output is machine-readable and renderable:

InvestigationReport {
  summary, impact (abs, %, estimated revenue at risk),
  root_causes: [{hypothesis, confidence, evidence_ids[], contribution_pct}],
  ruled_out: [{hypothesis, why}],
  similar_past_cases: [{id, similarity, outcome}],
  recommended_actions: [{action, owner_hint, priority, expected_effect}],
  open_questions, data_quality_notes,
  trace_id, tools_used, duration, tokens_used
}

Every claim must cite evidence_ids. Reject reports with uncited claims (auto-retry once).

L9: Experience Layer (Streamlit + Plotly)

Pages:

  1. Alert Inbox: list of anomalies with severity, one-click "Investigate".
  2. Live Investigation: streaming timeline of agent steps (planning, tool call, evidence found, memory recalled, hypothesis added/killed) with Plotly charts appearing as evidence arrives. This is your demo centerpiece.
  3. Report View: summary, waterfall chart of contribution by segment, ranked causes with confidence bars, evidence drill-down, ruled-out list.
  4. Feedback Panel: "Confirm cause / Wrong cause / Partially", action taken, outcome. This triggers Hindsight retain.
  5. Memory Explorer: past investigations, recall hits shown per run, org insights.
  6. Impact Dashboard: MTTR before vs. after memory, hypothesis accuracy over time, tool calls per investigation.

3. End-to-End Runtime Flow

  1. Alert arrives (webhook/simulator), normalized into Anomaly, investigation record created.
  2. Scoping: analyze_metric confirms the anomaly is real, finds the changepoint, checks data quality.
  3. Recall #1: Hindsight queried with the anomaly signature; top cases attached as priors.
  4. Planner produces a plan informed by the priors.
  5. Evidence gathering: breakdown_by_dimension, find_related_metrics, query_business_events (and logs). Each returns an evidence item with a chart.
  6. Recall #2: Hindsight queried with actual findings for evidence-matched cases.
  7. Hypothesizer generates 3 to 5 ranked hypotheses with predicted evidence.
  8. Validation loop: Critic requests targeted tools (cohort comparison, counterfactual, log check). Confidence computed by L7. Kill weak hypotheses, loop if below threshold (bounded).
  9. Report generated, validated against schema and citation rule.
  10. Human decides and acts, then submits feedback and outcome.
  11. Retain: the closed investigation (evidence, cause, action, outcome, was-agent-right) is written to Hindsight.
  12. Metrics updated: MTTR, accuracy, steps saved, feeding the impact dashboard.

6. Demo Script (3 to 4 minutes)

  1. Problem (20s): "Alerts tell you that revenue dropped. Finding why takes hours."
  2. Case 1, cold start (60s): Trigger the alert. Show the live timeline, the driver waterfall, ruled-out hypotheses, and the final report. Mark the confirmed cause and the rollback action. Memory is retained.
  3. Case 2, similar incident (60s): Trigger a related anomaly. Show the memory recall card ("similar to INV-001"), fewer tool calls, faster time-to-cause.
  4. Case 3, false alarm (30s): Agent identifies a tracking bug and says the business is fine.
  5. Learning curve (40s): Show the chart across 10 to 20 incidents (with and without memory), MTTR reduction and the reflect-generated org insights.
  6. Close (20s): Read-only, auditable, human-in-the-loop, plugs into any monitoring stack.

7. Pitfalls to Avoid

  • Letting the LLM write arbitrary SQL. Use typed tools.
  • Sending raw rows to the LLM. Send aggregates and compact evidence.
  • Treating memory as truth. Use it as priors that must be validated.
  • Presenting one confident answer. Show ranked hypotheses plus what was ruled out.
  • Skipping measurement. If you cannot show "faster with memory", the Hindsight story is just a claim.
  • Ignoring function-calling failures. The brief explicitly warns about them.
  • Building the whole roadmap. Ship the demo path first.

8. Path to Adoption (Real-World Impact)

  • Buyers/users: data and BI teams, SRE/operations, revenue operations, e-commerce and fintech companies with many KPIs.
  • Pain: each anomaly costs hours of dashboard and SQL digging, and similar cases are re-investigated from scratch.
  • Integration: alerts from Grafana, Datadog or a scheduled monitor; reports posted to Slack; read-only access to the warehouse.
  • Value proof: report your measured numbers, e.g. "median steps to root cause fell from X to Y over 20 incidents."
  • Pricing story: per-seat or per-monitored-KPI subscription; clears the brief's "would someone pay $50/month" test.
